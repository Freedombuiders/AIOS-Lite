# RocketFlow inside ClaudeClaw

> **Superseded UI (2026-10-20).** The **Tạo video mới** tab described below was removed in Video Studio v3. Creation now happens in the **Studio** workspace with the Đạo diễn AI, where RocketFlow is one scene engine among HeyGen, Veo, fal and Pexels. See [video-studio-production.md](video-studio-production.md). The RocketFlow setup steps below still apply. The `/creation/*` routes and the `video-create` tools remain only for compatibility.

Video Studio had two tabs: **Dựng video có sẵn** (now **Video quay sẵn**) preserves the raw-footage StudioShell workflow; **Tạo video mới** briefed an agent using the repo-managed `video-create` skill. That agent discovers Google Flow image/video capabilities, plans scenes, generates real assets through the shared RocketFlow service, imports verified downloads and queues local MP4 assembly. `?tab=flow` now opens the Studio workspace.

## Setup on one computer

1. Run the ClaudeClaw dashboard and Chrome on the **same computer**, with the same ClaudeClaw store/config used by agent processes. Install/reload the updated RocketFlow extension. Install its MCP dependencies with `npm install` in `rocketflow/mcp-server` if needed.
2. The default bridge path is `../rocketflow-extension/rocketflow/mcp-server/index.mjs` relative to ClaudeClaw's application root. For a packaged/different layout set `ROCKETFLOW_MCP_SERVER` to that absolute file path, then restart the app. Build the server so `dist/mcp-hub-server.js` exists.
3. Enable MCP control in RocketFlow and open Chrome on the same machine. Connection is automatic: no pairing code or credential input. The shared settings panel shows connection status and agent grants.
4. RocketFlow reconnects every 30 seconds to loopback port **17898**, outside the legacy MCP range 17893–17897. When the app acknowledges the connection, the extension ignores commands from legacy controllers until the app disconnects. Existing saved pairing keys are ignored. **Kiểm tra kết nối** reports actual status.
5. Grant an agent explicitly in the same panel. `video-editor` is prefilled, but **no agent is granted by default**. `read` permits status, capabilities and reading its own jobs; `write` additionally permits generation and cancellation of its own jobs. Choose `off` to revoke. Updated grants apply to calls in existing turns; upgrades need a new turn to expose additional tools.

Keep the Flow tab visible when generating. Account/build/license/provider restrictions still come from the installed RocketFlow version; the app does not bypass them. No generation happens during setup/status checks.

The internal `agent-service.key` still authenticates trusted agent processes to the app; it is not a user-facing pairing code. User-agent grants and own-job checks remain enforced. Old `pairing.key` files are unused.

## Agent-driven creation

1. Open **Tạo video mới**, select a configured Claude or Codex agent, and chat. The agent still needs the repo `video-create` skill and RocketFlow write grant; existing live settings are never overwritten. No brand/model/duration/consent form is required. A default brand profile supplies local renderer settings when needed.
2. Ask for a storyboard, ask questions, or explicitly tell the agent to create. The agent interprets the natural-language request using `create_brief`, including exact total duration, number/length of clips, aspect, model/type/audio and `plan` versus `generate` intent. The host binds this to the latest owner message. A literal quote of an explicit creation instruction is required for paid generation; questions and planning-only requests remain unauthorized. New messages revoke permission to submit additional scenes until the current instruction is confirmed. Poll/import/render of already submitted work remains available.
3. Example: **“tạo storyboard video mẹ bé, rồi tạo đi, video 16s ghép bởi 2 cái lại”** means two video clips, each generated at 8s, assembled into 16s. The agent discovers models and 8s support from Flow before dispatch. Unsupported durations/models are reported, not silently replaced. Missing nonessential choices default to 9:16, native clip audio and a discovered compatible model; a user's exact duration/model overrides defaults.
4. Chat messages, saved storyboard, scenes, previews, render progress and final MP4 remain in the creation conversation. Further chat uses the same scoped director, including the existing project `/messages` API. A question cannot reuse a previous message's generation authorization. New-project submissions and follow-up chat requests use stable UUIDs for deduplication. Unknown provider submissions are never replayed. Stopping the agent does not undo Flow work already sent.

Tools: `create_context`, `create_brief`, `flow_capabilities`, `create_plan`, `create_generate`, `create_poll`, `create_import`, `create_render`, `create_status`, `create_cancel`. Metadata/storyboard is generated by the agent, not a regex storyboard template. The host's conservative explicit-instruction guard is only an authorization check; ambiguous commands should be clarified. The app injects the allowed creation skill into each turn, without changing global agent configuration.

Creation projects live under `STORE_DIR/video-edit`; they have `mode=create`, a persisted brief/scene state, library asset IDs, verified project media and final render records. Raw-edit projects retain their old schema and workflow and are listed separately. Initial chat submissions are reserved by UUID before starting an agent, so repeated HTTP submissions do not start another credit-using turn. A crash before binding the reservation to a project is reported for inspection, not retried.

Downloads must remain under `~/Downloads/RocketFlow/studio-<requestId>/`; set **ROCKETFLOW_DOWNLOAD_ROOT** on the app if Chrome uses a different RocketFlow root. Chrome and server must share this local filesystem. The host reads structured `get_job_details`, validates batch/prompt/type/provenance and real paths, checks file magic and media metadata, and copies only matching downloaded files into the library/project. Remote URLs are not imported. Reload/update the extension MCP server to get this new read-only tool.

Local assembly uses installed ffmpeg/ffprobe (including libx264 and the subtitles/libass filter), the existing serial machine-job queue and project media serving. It normalizes scenes to 720p/30fps, preserves their order, trims video from its beginning, holds still images, adds per-scene text and retains native clip audio or creates silence. It probes the final file before marking it complete. This MVP has no generated narration, music, avatar, image animation or advanced transitions. Plans become immutable once generation starts; a materially different brief is a new project and a new credit authorization. Queued renders resume; interrupted renders become failed and can be explicitly resumed using imported files. No generation is replayed to repair a render.

General authorized agent turns still receive `rocketflow_status`, `rocketflow_capabilities`, `rocketflow_generate`, `rocketflow_get`, `rocketflow_cancel` through the shared service. They use durable app job UUIDs, never arbitrary extension batch IDs. Explicitly restricted general turns remain restricted. Creation is a separate host-owned restricted task with only its project tools, including when the agent's ordinary chat context is lean. Codex receives no native shell, network, host apps or broad filesystem writes; Claude receives an empty native tool set and only scoped MCP. Low-trust agents cannot use this task. Per-call skill/grant checks fail closed after revocation.

## Architecture and access boundary

- The dashboard owns the `RocketFlowService` singleton, starts its persistent stdio bridge at app startup, and closes it with the dashboard server. The bridge runs the existing RocketFlow MCP server, which hosts loopback WebSocket transport. No subprocess is spawned per poll or agent turn.
- Separate agent processes forward fixed, validated tool operations to the running app's authenticated `/api/video-studio/agent-call` endpoint. They never open their own extension connection. If the dashboard is stopped/unavailable, calls fail; there is no fallback write path.
- Each authorized turn gets a short-lived random capability and loopback gateway using the existing `mcp-hub-server.js` stdio adapter. The subprocess receives only that turn capability. Gateway cleanup runs on completion/abort. Host identity is supplied by the runtime, not tool arguments. The app rechecks grants and job ownership before execution.
- Tool-less turns, turns with explicit tool allowlists or MCP denials, unsupported engines, and low-trust agents receive no RocketFlow tools. Low-trust support would need an explicit approval workflow and is deliberately unavailable here.
- Automatic extension transport binds only to 127.0.0.1, requires a well-formed Chrome extension Origin and matching hello extension ID, accepts results only from the active socket, and refuses takeover of a live connection. No shared secret is required for this local extension transport. This blocks ordinary web-page clients, but does not authenticate local native programs or prove that another installed extension is RocketFlow; the design assumes a trusted local machine. Agent-to-app capabilities and grants remain authenticated separately.
- Existing dashboard authentication, CSRF policy and mutation kill switch apply to Studio and app agent entry points. Jobs/grants/keys live under `STORE_DIR/video-studio` with private file permissions. Grant changes and job snapshots use atomic replacement; submission reserves a UUID exclusively before any upstream await.
- All generation enters RocketFlow's **existing shared queue**, with sequential mode requested. Studio and agent jobs therefore use the same queue coordination as manual RocketFlow work. The app does not introduce a competing runner, clear/resume the queue, or bypass extension queue locks.

## Reliability limits

Submission and cancellation are never automatically replayed on reconnect, timeout, process restart, or uncertain responses. A disconnect rejects pending bridge calls. An interrupted submission is shown as `unknown`; its UUID remains reserved. Cancellation attempts are also reserved, and an uncertain cancellation cannot be sent again automatically. Refresh is safe to repeat, but no automatic refresh loop submits work.

App IDs, provenance and last returned text/results survive restart. The extension's batch ID is stored once acknowledged. There is **no distributed exactly-once guarantee**: if the extension enqueues work and the acknowledgement is lost, the app cannot recover the batch ID or reconcile it automatically. Inspect RocketFlow's queue before making any new batch. Extension reload, agent-tab closure or provider changes can lose extension-side jobs even while app history remains. A stalled extension command may continue after the app gateway closes. Cancellation cannot undo provider work already submitted. Shared jobs retain their last extension response and submission outcome; creation projects additionally persist scene/import/render state. Polling is agent-driven, not a daemon: while the agent is stopped the UI shows the last saved Flow scene state. Resume to refresh it. There is no background automatic generation or unknown-job reconciliation.

Extension heartbeat keeps the service worker active but is not an application-level liveness guarantee. A dead peer is detected by socket close or request timeout. Dependencies/the updated sibling extension must be installed; packaged distribution of RocketFlow itself is not added here. Creation project previews and final outputs are served through authenticated dashboard media routes after verified local import. Other legacy shared-job results still expose local paths.

The reused machine-job queue logs interrupted work but its existing persistence is best effort if disk writes fail; this change does not claim durability through filesystem failures.

Validation uses mocked extension/provider responses and no paid requests; live Google Flow generation has not been tested by this change.
